## 발견 사항

### 1. [백엔드 버그, 수정 완료] `GuestTicketRefundEligibilityService` 트랜잭션 버그
`@Transactional(readOnly = true)`인데 내부에서 부르는 `verifyGuestOrderAccess()`가 항상
`guest_order_infos`에 쓰기 락을 거는 구조라 PostgreSQL이 거부(500). `readOnly` 제거로 수정,
재기동 후 실측 확인.

### 2. [문서 오류, 수정 완료] `screen-api-map.md`의 결제·환불 상태 표기가 낡아 있었음
"티켓 예매(회원·비회원)"의 결제, "비회원 주문 상세"의 환불이 ⚠️(API 없음)로 남아있었는데
이번 세션에 프론트 연동까지 전부 완료됐다. 4절 "준비 중 화면" 목록에서도 결제·환불 항목을
제거하고 해소 목록으로 옮김. → 수정 완료(별도 커밋).

### 3. [자동화 이슈, 앱 버그 아님] 카테고리 "비활성화" 네이티브 confirm() 다이얼로그
자동화 클릭 도중 `window.confirm()`이 떠서 브라우저가 잠깐 멈췄고(도구로 못 닫음, 사용자가 직접
닫아줌), 그 과정에서 스크립트가 엉뚱한 행(IT/전자)을 비활성화하는 부작용이 생겨 API로 직접 되돌림
(IT/전자 재활성화, 테스트로 만든 카테고리는 비활성 처리). **최종 데이터 상태는 정상.** 참고로
이 버튼만 브라우저 네이티브 confirm을 쓰고 다른 화면들은 인앱 컴포넌트를 쓰는데, UX 일관성 관점
에서 살짝 아쉬운 부분.

### 4. [정보, 버그 아님] 회원가입 이메일/휴대폰 인증코드는 로컬에서 확인 불가
`LoggingEmailSender`가 보안 컨벤션상 인증코드를 어떤 로그 레벨에도 남기지 않도록 의도적으로
설계돼 있다(AGENTS.md 근거). 그래서 브라우저 자동화로 신규 회원가입을 처음부터 끝까지 완주하는
건 로컬 SMTP 없이는 불가능 — 버그 아니라 의도된 정책.

### 5. [정보, 버그 아님] 정산 리포트 "0원"
실제 DB 값도 0.00 (정산 `calculate` API가 이 seed 건에는 안 걸림) — 프론트 표시 문제 아님.
